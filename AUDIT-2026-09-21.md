## 1. Executive summary — the ten things I'd look at first

1. **C-01 🔴** `quad_contains` hit-tests the wrong half of the quad for any non-center anchor (Y is not flipped the way the shader flips it). Latent today only because every anchor in the demo/example is `(0.5, 0.5)`.
2. **C-02 🔴** Hit-test "topmost wins" still uses raw ECS iteration order — the exact cross-archetype bug M13.8 fixed for *drawing* (`SpawnOrder`) was not applied to *input*, and `z` is ignored entirely. Two overlapping interactables can draw one way and click the other.
3. **C-03 🔴** `ProteusConfig::desktop()` (page_size 4096) breaks every untextured quad: `WHITE_PIXEL_UV_OFFSET` is hard-coded to a 2048 page, so on a 4096 page it samples the texel *boundary* and bilinear-blends the white sentinel with three empty texels (~25 % white).
4. **C-04 🔴** Most `Handle` methods call `World::entity_mut(self.0)`, which **panics** on a despawned entity — but three separate doc comments promise stale handles "no-op". In the wasm SDK a panic kills the page.
5. **C-05 🔴** The demo never re-applies the viewport after startup: `DemoApp::update` ignores `Frame::viewport`, so resizing the native window leaves the background at 1280×800 and nav/theme icons pinned to the old corners. (Web is unaffected only because the canvas is fixed-size CSS.)
6. **A-01 🔴** The SDK (Rust and TS) has **no way to show or hide a component**, and `signal.set()` never reveals a hidden `to`. The canonical Phase A round-trip (button → list → button) is impossible without destroying and recreating entities — which is exactly what `examples/gallery` does, and why it leaks (C-06).
7. **C-06 🟠** `Handle::destroy` never removes that entity's callbacks from `CallbackRegistry`; the TS example also creates a fresh `app.signal()` per click and never destroys it. Long-running destroy/rebuild apps grow without bound.
8. **R-01 🔴** `pages.yml` / `staging-deploy.yml` only trigger on `proteus-gpu|render|ui|shell-web` paths. A change to `proteus-demo` (where *all* demo logic now lives), `proteus-runtime`, `proteus-host-web`, `proteus-sdk(-web)`, or `Cargo.lock` will **not** redeploy the live demo.
9. **X-01 🟠** `proteus-gpu` is a dead crate (nothing imports it; `proteus-render` defines its own `GpuContext`), yet README/VISION/PLANNING all describe it as "Layer 0". Plus a cluster of dead public API in `proteus-render` (the whole `VideoFrameSender`/`consume_video_frame`/`resume_video` channel), `proteus-ui` (`vertical_slices`, `collect_entity_instances`, `TransitionComplete`, `ActiveGroupTransition.total`), and the host crates (every "M13.4-debt shim" accessor that outlived the shim).
10. **D-01 🟠** The docs have drifted materially since M13 closed: README says M13 is "in progress" and omits two crates; VISION lists 5 of 11 crates and "M0 through M12"; PLANNING's M13.1/M13.3 DoD boxes are all unchecked though built, M8.5 claims a `blur.rs` skeleton that ROADMAP says was deleted, M13.2 says no staging environment exists though M12.5 created one; ~160 comments in `proteus-demo` still say "mirrors `proteus-shell-native::…`" about code that was deleted at the M12.5 cutover.

## 2. Correctness & robustness (C)

### C-01 🔴 ✅ FIXED (2026-09-22) — `quad_contains` ignores the anchor Y-flip — hit box is vertically mirrored for non-center anchors
*Resolution:* Y extents re-derived from `quad.wgsl`'s own `anchor_shift`, with the derivation written next to them so the next reader doesn't "simplify" it back. Doc corrected to say world-space (was K-12). Regression test `top_left_anchored_quad_is_clickable_where_it_renders_not_mirrored_above_it`; confirmed it fails against the pre-fix formula.

- **Where:** [`crates/proteus-ui/src/input.rs:198-207`](crates/proteus-ui/src/input.rs:198)
- **What:** The shader (`quad.wgsl` `vs_main`, and `mesh.rs`'s `transform_top_left_anchor` test) treats `anchor` as Y-down: anchor `(0,0)` pins the quad's **top-left** corner to `position`, so the quad extends right and *down* (negative world-Y). `quad_contains` computes `min = -anchor*size`, `max = (1-anchor)*size` on both axes — for anchor `(0,0)` that is `y ∈ [0, h)`, i.e. *up*. For `(0,1)` it's the opposite mismatch. Only `anchor.y == 0.5` agrees.
- **Why it matters:** Any SDK user who sets a non-center anchor on an interactive component (the TS `Geometry.anchor` field is public and documented "Y-down: [0,0] = top-left") gets a click region that is the mirror image of what's drawn. Not caught because every fixture in `hit_test.rs` and every anchor in the demo/example is `(0.5, 0.5)`.
- **Suggested action:** Flip Y in `quad_contains`: `min.y = -(1 - anchor.y) * h`, `max.y = anchor.y * h`. Add a `hit_test.rs` case with anchor `(0,0)` that asserts a point just *below* `position` hits and a point just above misses. Also fix the doc on line 178 ("window-space pixels, origin top-left") — the point is world-space, center-origin, Y-up, per `PointerInput`'s own doc.

### C-02 🔴 ✅ FIXED (2026-09-22) — Hit-test resolution order ≠ draw order (z ignored, cross-archetype order undefined)
*Resolution:* hit-testing now picks the greatest `(world z, SpawnOrder)` — the same key `collect_instances` sorts roots on. Two regression tests (`higher_z_entity_wins_even_though_it_was_spawned_first`, `overlap_is_decided_by_spawn_order_across_archetypes`), both confirmed failing against the pre-fix selection.
**The audit understated this one.** I expected the archetype case to need a third entity to trigger, as the M13.8 rendering repro did. It doesn't: two overlapping interactables in different archetypes already resolved in *reverse*-spawn order with nothing perturbing them — the first assertion fails outright. **Residual gap, deliberately left and documented in `input.rs`:** the renderer walks each root's subtree depth-first, so one global sort key can still disagree for a child with an explicit nonzero `z`, or one re-parented under a later-spawned parent. Closing that means hit-testing against the renderer's own ordering rather than a second approximation of it — a bigger change than this fix, and worth its own decision.

- **Where:** [`crates/proteus-ui/src/input.rs:284-303`](crates/proteus-ui/src/input.rs:284) ("last hit wins, matches draw order")
- **What:** Draw order is now `(z asc, SpawnOrder asc)` per root with a depth-first child walk (`collect.rs`). The hit loop iterates the flat query in archetype order and takes the *last* containing entity: `position.z` is never consulted, and the archetype-order problem that M13.8 proved for rendering (`spawning_into_an_existing_archetype_does_not_reorder_a_different_archetype`) applies identically here. `hit_test.rs::top_draw_order_entity_wins_when_quads_overlap` only spawns two entities in the *same* archetype, so it can't see it.
- **Why it matters:** A background spawned first (no `Interactable`? then it's excluded — but any two *interactable* overlapping entities in different archetypes, e.g. one with `InteractionDef` and one without) can render one on top and deliver the click to the other. Also an explicit `z` layering that is honored visually is not honored for input.
- **Suggested action:** Collect candidates with `(z, SpawnOrder)` and pick the max, or reuse `collect.rs`'s root sort + depth-first walk so input and render share one ordering. Add a test mirroring the M13.8 repro for hit-testing.

### C-03 🔴 ✅ FIXED (2026-09-22) — `WHITE_PIXEL_UV_OFFSET` is computed from the *default* page size, not the configured one
*Resolution:* sentinel now samples the atlas corner `(0, 0)`, correct at any page size via `ClampToEdge`, plus the whole reserved guard block is filled white as a second, independent guarantee. Measured against the old constant at 4096: a full-red quad read back `[64, 191, 0, 255]` — the predicted 25%. GPU regression test `untextured_quad_renders_at_full_intensity_on_a_non_default_page_size` (skips if the adapter can't do 4096).

- **Where:** [`crates/proteus-render/src/pipeline.rs:316-319`](crates/proteus-render/src/pipeline.rs:316) (`0.5 / DEFAULT_MAIN_ATLAS_SIZE`), used by [`collect.rs:199`](crates/proteus-ui/src/collect.rs:199); preset at [`crates/proteus-runtime/src/config.rs:66`](crates/proteus-runtime/src/config.rs:66)
- **What:** With `AtlasConfig::page_size = 4096` (`ProteusConfig::desktop()`), `0.5/2048` lands at pixel coordinate `1.0` — exactly the boundary between texel 0 (white) and texel 1 (never written, zero-initialized, inside the 4×4 guard). Linear filtering yields ≈25 % white / 75 % transparent for every solid-color quad. `page_size = 1024` (`constrained()`) happens to still land inside texel 0, so only sizes > 2048 break.
- **Why it matters:** `desktop()` is a public, documented preset whose one job is bigger atlases; using it makes the whole UI wash out. Not caught because no host or test uses either preset.
- **Suggested action:** Make the sentinel UV a method on `QuadPipeline`/`TextureRegistry` derived from `page_size` (or store it in the `TextureRegistry` next to `page_size`), and have `collect.rs` read it from the world resource. Add a headless test that constructs a 4096-page pipeline (skip if the adapter's limit is lower) and asserts a solid red quad reads back ~255.

### C-04 🔴 ✅ FIXED (2026-09-22) — Stale `Handle`s panic instead of no-op-ing — contradicting three doc comments
*Resolution:* `Result<_, HandleError>` + `warn!` on every fallible method; "nothing to do" stays an `Ok` value so routine polling isn't reported as failure. TS surface unchanged (wasm-bindgen maps `Result<T, JsValue>` to `T` and throws). All three stale docs corrected. Four regression tests, one calling all sixteen mutating methods on a destroyed handle.

- **Where:** [`crates/proteus-sdk/src/handle.rs`](crates/proteus-sdk/src/handle.rs) — 13 calls to `app.world.world.entity_mut(self.0)` (`set_declared_geometry`, `animate_to`, `start_video`, `stop_video`, `set_interactive`, `copy_baked_image_from`, `center_crop_to_square`, `split_to`, `split_to_with_states`, `merge_from`, `add_child`, `remove_child(destroy=false)`, `free_resources`, `set_texture`). `bevy_ecs::World::entity_mut` panics if the entity does not exist.
- **Docs that promise otherwise:** [`handle.rs:58`](crates/proteus-sdk/src/handle.rs:58) ("methods no-op or `Proteus::get` returns `None`"), [`proteus-sdk-web/src/handle.rs:38`](crates/proteus-sdk-web/src/handle.rs:38) ("methods become no-ops"), and the TS `handleFromId` JSDoc.
- **Why it matters:** In TS, `app.handleFromId(staleId).animateTo(...)` — or any handle kept across a `destroy()` of the same entity — aborts the wasm module; the canvas freezes with no recovery. The gallery example keeps handles in closures past `destroySoon` timers, so this is one race away from reproducing.
- **Suggested action:** Use `get_entity_mut` and early-return (or return `bool`/`Result`) in every `Handle` method; make `remove_child` tolerate a dead child. Add a test: destroy then call each method; nothing panics.

### C-05 🔴 ✅ FIXED (2026-09-22) — Demo layout never tracks window resize after startup
*Resolution:* `DemoApp::update` forwards a changed `Frame::viewport` to `Demo::set_viewport_size`, on change only (it rewrites declared geometry, so every-frame would clobber a tile mid-transition). Test drives the real `App::update` through a real `Frame` against a stub `HostServices`.

- **Where:** [`crates/proteus-demo/src/app.rs:229`](crates/proteus-demo/src/app.rs:229) is the only `set_viewport_size` call (in `setup`); `update` only reads `f.viewport.scale_factor` for fetch sizing.
- **What:** `Demo::set_viewport_size`'s own doc says "Call on every resize". `Engine::resize` updates `Frame::viewport`, but `DemoApp::update` never forwards it, so `background.light/dark` stay 1280×800, gallery declared geometry stays stale, and `advance_nav_icons`/`advance_theme` keep positioning against the startup `viewport_size`.
- **Why it matters:** Resizing the native window (or a future non-fixed-size canvas) produces a visibly broken layout. This is a regression from the pre-M13 shells, which called it on `Resized`. Not covered by tests (the `Harness` never resizes).
- **Suggested action:** In `DemoApp::update`, compare `f.viewport.logical_size` to the last-seen value and call `demo.set_viewport_size` on change (or add an `App::resize` hook to the contract). Add a demo test that ticks, changes the viewport, and asserts the background size follows.

### C-06 🟠 ✅ FIXED (2026-09-22) — Callback registry and signal registry leak on destroy/rebuild patterns
*Resolution:* handlers forgotten across the destroyed subtree, plus the `on_dropped` handlers of any signals those entities owned; `SignalHandle::destroy` prunes too. Also fixed a case the audit didn't spot: dispatch's take-call-put-back holds handlers outside the map during the call, so a callback destroying its own component had them resurrected afterwards — the put-back is now conditional on the entity still existing. Four tests. *Not covered:* a despawn made directly through `Proteus::world_mut()`, documented at `forget_subtree`. The gallery example's per-click `app.signal()` is an example-side issue, still open — see A-01.
- **Where:** [`crates/proteus-sdk/src/handle.rs:422`](crates/proteus-sdk/src/handle.rs:422) (`destroy` only despawns); [`crates/proteus-sdk/src/callback.rs`](crates/proteus-sdk/src/callback.rs) (`HashMap<(Entity, EventKind), Vec<Box<dyn FnMut>>>` never pruned); [`examples/gallery/src/main.ts:319`](examples/gallery/src/main.ts:319) (`const sig = app.signal();` per click, never destroyed).
- **What:** `Handle::destroy`/`remove_child(destroy: true)` leave every `on_*` closure keyed by the dead `Entity` in the registry forever (Entity generations mean keys never collide, so they're never overwritten either). The TS example — the framework's own M14 reference — destroys and recreates 12 tiles with `onClick` handlers per cycle and mints an unowned signal per navigation.
- **Suggested action:** Prune `handlers`/`drag_handlers` for the entity in `destroy` (and consider an `on_remove` hook on a marker component so `world.despawn` from any path cleans up). Either destroy the example's signals or create one owned signal per app and reuse it — the latter also demonstrates the Phase A model the docs describe.

### C-07 🟠 ✅ FIXED (2026-09-22) — Group-transition virtuals are orphaned if the coordinator disappears
*Resolution:* fixed at the ownership level rather than by bolting on a second cleanup path — `transition_atlas` regions are now released by `on_remove` hooks on `ActiveGroupTransition` and `BakedTexture`, mirroring `TextureRef`'s handling of `main_atlas`. The explicit frees came *out* of the completion system, since keeping both would double-free. Orphaned virtuals are despawned with a warning instead of stranded.
- **Where:** [`crates/proteus-ui/src/topology.rs:1080-1082`](crates/proteus-ui/src/topology.rs:1080)
- **What:** `group_transition_complete_system` `continue`s when `coordinators.get_mut(coord_entity)` fails. If the source (1→N) or destination (N→1) entity is despawned mid-transition — or its `ActiveGroupTransition` is removed — its `Virtual` slices are never despawned, keep rendering at their settled state forever, and every `BakedTexture::own_alloc` region plus the `shared_alloc` in `transition_atlas` is never freed.
- **Suggested action:** Treat a missing coordinator as "finalize anyway": despawn the virtuals and free their `own_alloc`s (the shared alloc is lost with the coordinator; consider moving it onto a virtual or a dedicated bookkeeping entity). Add a test that despawns the source mid-split.

### C-08 🟠 ✅ FIXED (2026-09-22) — Delayed transitions don't snap to `from_state` during the delay
*Resolution:* `transition_setup_system` now writes `from` alongside `ActiveTransition`, fixing both the delay symptom and a second one the audit missed — even at zero delay, `ActiveTransition` is inserted via `Commands`, so the tick system doesn't see it until the next frame, leaving one rendered frame at the stale position (a flash of the end state for a signal-driven morph). Three tests; both symptom tests confirmed failing beforehand.
**I called the risk wrong here.** I flagged this as likely to change the demo's motion and to need visual review before landing. It can't: the demo uses only `Slice`/`GridSlice` (never `SplitStrategy::Bake`), never calls `SignalHandle::set`, sets `child_behavior: None` everywhere and `delay: 0.0` in every config — so every `TransitionRequest` it creates has `from_state: None`, where the write is a no-op. Proven rather than argued: with a probe panicking on any `from_state: Some` reaching the changed code, all 57 demo tests still pass. The one in-repo path that *is* affected is `examples/gallery` (`sig.set(...)`), which gets the one-frame flash removed.
- **Where:** [`crates/proteus-ui/src/transition.rs:244`](crates/proteus-ui/src/transition.rs:244) (`if effective_dt == 0.0 { continue; }`); `transition_setup_system` never writes `from` into `QuadState`.
- **What:** With `delay > 0` and `from_state: Some(..)` (signal dispatch, `SplitStrategy::Bake`, any stagger), the entity keeps rendering at its *own* pre-request `QuadState` for the whole delay, then jumps to `from` on the first lerp tick. For `Bake` + `child_behavior` stagger, every target is fully visible at its final position, then teleports to the source and animates back out — the opposite of a stagger.
- **Suggested action:** In `transition_setup_system`, when `from_state` is `Some`, also write it to the entity's `QuadState`; or in the tick system apply `from` while `delay_remaining > 0`. `topology_systems.rs::bake_1_to_n_child_behavior_overrides_config` only asserts durations — extend it to assert position during the delay.

### C-09 🟠 ✅ FIXED (2026-09-22) — `Mp4Stream::stop` can deadlock if the decode thread is blocked on `send`
*Resolution:* receiver dropped before the join. Test needs no `ffmpeg` (stand-in producer) and asserts under a timeout, since the failure mode is a hang. Also the first test in `proteus-host-winit`, which had none — a dent in T-05.

- **Where:** [`crates/proteus-host-winit/src/mp4_player.rs:123-132`](crates/proteus-host-winit/src/mp4_player.rs:123)
- **What:** `stop` sets the flag, kills ffmpeg, then `join`s the decode thread *before* `self.rx` is dropped (it drops at the end of `stop`). If the thread is parked in `tx.send(buf)` because the 2-slot channel is full (the app stopped polling a few frames before calling `stop_video`), killing ffmpeg doesn't unblock `send`, and `join` never returns — the render thread hangs.
- **Suggested action:** Drop/drain `rx` (or move `rx` into an `Option` and `take()` it) before `join`, or use `try_send` in the decode loop.

### C-10 🟠 `bake_texture`/`load_texture` hand back an eviction-eligible handle
- **Where:** [`crates/proteus-runtime/src/bake.rs`](crates/proteus-runtime/src/bake.rs) `bake_texture` → `register_static(.., req.eternal)` with `ref_count == 0`
- **What:** Until the caller attaches the handle via `Handle::set_texture` (which inserts the `TextureRef` that increfs), the region is a reclaim candidate. Any registration under pressure in between — e.g. a loop calling `load_texture` N times before attaching any — can evict earlier results silently (`set_texture` then returns `false`). The demo is safe only because it attaches immediately after each bake and the logo frames are `eternal`.
- **Suggested action:** Either document the "attach immediately" contract on `Frame::load_texture`/`bake_texture` and `TextureHandle`, or return handles that hold a provisional reference released on drop/attach.

### C-11 🟠 ✅ FIXED (2026-09-22) — `InteractionState.declared` is captured once and never refreshed
*Resolution:* `set_declared_geometry` updates the style system's snapshot as well as `DeclaredGeometry`. Test covers the full hover→leave round trip returning to the *new* rest geometry.
- **Where:** [`crates/proteus-ui/src/interaction.rs:182`](crates/proteus-ui/src/interaction.rs:182); `Handle::set_declared_geometry`/`animate_to` don't touch it.
- **What:** A component with hover/pressed styles whose rest geometry is later changed via `set_declared_geometry` or `animate_to` returns to the *original* captured geometry when the interaction state goes back to `Default` — the classic "hover exit snaps the button back to where it was spawned". The reference demo doesn't hit this because it never uses `InteractionDef` at all (see T-06); the TS example's tiles do use `hover: { scale }` but don't move after spawn.
- **Suggested action:** Have `set_declared_geometry` also update `InteractionState.declared` (or have the style system read `DeclaredGeometry` when present instead of its own snapshot). Add an `interaction_systems.rs` test.

### C-12 🟠 Web host: JS `update` runs while the `WebLoop` `RefCell` is mutably borrowed
- **Where:** [`crates/proteus-host-web/src/lib.rs`](crates/proteus-host-web/src/lib.rs) `start_raf_loop` → `state.borrow_mut().render_frame(..)` → `JsDriver::frame` → `update.call1(..)`
- **What:** The M13.8 fix defers *callbacks* to microtasks, but the per-frame `update` JS function is invoked synchronously inside `render_frame` while `state` is borrowed. Anything in `update` that synchronously dispatches a canvas pointer event (`canvas.dispatchEvent(new PointerEvent(...))`, as PLANNING's own automation attempts did) re-enters `wire_pointer`'s `borrow_mut()` → "already borrowed" panic.
- **Suggested action:** Release the `WebLoop` borrow around the JS call (take the driver out, call, put back), or document the restriction on `MountOptions.update`.

### C-13 🟡 JS callback exceptions are silently swallowed
- **Where:** [`crates/proteus-sdk-web/src/lib.rs:118`](crates/proteus-sdk-web/src/lib.rs:118) and the two sibling wrappers (`let _ = cb.call…`)
- **What:** A `throw` inside `onClick` etc. vanishes (the comment even says so); `update` errors *are* logged in `js_app.rs`. Inconsistent, and a real DX trap for the "agentic" audience.
- **Suggested action:** `console.error` (via `web_sys::console::error_1`) on `Err`, matching `JsDriver::frame`.

### C-14 🟡 `signal.set(to, from)` with `to == from` hides the transitioning entity
- **Where:** [`crates/proteus-ui/src/signal.rs:365-371`](crates/proteus-ui/src/signal.rs:365)
- **What:** Dispatch inserts the request on `to` then hides `from`; if they're the same entity the morph runs invisibly. Not validated as a drop reason.
- **Suggested action:** Add `DropReason::SameEntity` (or route to `Handle::animate_to` semantics).

### C-15 🟡 `bake_system` double-renders a `Text` that lives on the baked root itself
- **Where:** [`crates/proteus-ui/src/bake.rs:200-209`](crates/proteus-ui/src/bake.rs:200) removes `Border`/`Glow`/`DropShadow` but not `BakedText`/`Text`; [`collect.rs`](crates/proteus-ui/src/collect.rs) still emits the text overlay for any entity carrying `BakedText`.
- **What:** `component(spec.text(..).bake())` bakes the label into the composite *and* keeps drawing the overlay on top. Works today only because the demo always puts text on a child.
- **Suggested action:** Remove `BakedText`+`Text` (and `BakedImage`) from the root after a successful bake, or skip the overlay when `BakedComposite` is present.

### C-16 🟡 ✅ FIXED (2026-09-22) — Video registry entries are never freed
*Resolution:* `Frame::stop_video` frees the entry after suspending. Tested at the real call site with a GPU-backed test rather than only the registry capability underneath — which required giving `proteus-runtime` its first headless-device test.
- **Where:** [`crates/proteus-render/src/texture_registry.rs:311`](crates/proteus-render/src/texture_registry.rs:311) `register_video` on every `init_video`; [`proteus-runtime/src/app.rs`](crates/proteus-runtime/src/app.rs) `stop_video` → `suspend_video` only marks `Evicted`.
- **What:** Each play adds a `Video` entry; nothing removes it (`is_eviction_candidate` excludes `Video`). Metadata-only, so it's a slow leak, but `resident`/`info` queries accumulate ghosts.
- **Suggested action:** `free` the id in `stop_video` (or make `suspend_video` remove the entry).

### C-17 🟡 `FontAtlas` rasterizer clips glyphs with a negative left bearing on the first glyph
- **Where:** [`crates/proteus-render/src/font_atlas.rs`](crates/proteus-render/src/font_atlas.rs) — width is `max_right` over pen advances; a first glyph with `metrics.xmin < 0` gets `px < 0` and is skipped by the bounds check.
- **What:** The M11.3 right-edge fix has no left-edge counterpart. Inter Bold's Latin set rarely has negative `xmin`, so it's currently invisible; custom fonts (now wired via `TextConfig.default_font`) may not be.
- **Suggested action:** Track `min_left` alongside `max_right` and offset the pen by `-min_left`.

### C-18 🟡 Fetch threads on native have no timeout and can't be cancelled
- **Where:** [`crates/proteus-host-winit/src/lib.rs`](crates/proteus-host-winit/src/lib.rs) `fetch_url_bytes` — `ureq::get(url).call()` with default (no) timeout; `cancel_fetch` only drops the result.
- **What:** A hung picsum request pins a thread indefinitely; repeated gallery visits under a bad network accumulate threads. The app-level `GALLERY_FETCH_TIMEOUT_SECS` gives up on the *UI*, not the thread.
- **Suggested action:** Build an `ureq::Agent` with a connect/read timeout (or pass one through `HostServices`).

### C-19 ⚪ Per-frame overheads worth knowing before the stress-test numbers are trusted

## 8. API completeness vs. the Phase A/B design — things an M14 outside developer will hit (A)

These aren't bugs in what exists; they're places where the shipped SDK can't express what VISION/PLANNING promise, discovered by reading `examples/gallery` as that outside developer would.

- **A-01 🔴 No visibility control, and `signal.set` doesn't reveal `to`.** Phase A: components are "persistent … activated/deactivated via `visible`"; "`detail = component({ visible: false })` — inert until signal activates it"; the button → list → button round trip. Reality: `ComponentSpec` (Rust and TS) has no `visible`/`opacity`; `Handle` has no `set_visible`; `signal_dispatch_system` hides `from` but never shows `to`, so after `set(list, button)` the button is hidden and `set(button, list)` runs an *invisible* morph. The TS example's "back to grid" therefore rebuilds all 12 tiles from scratch every time. Suggested: add `visible`/`opacity` to the spec, `Handle::set_visible`/`set_opacity`, and make dispatch (or `SignalHandle::set`) set `to` visible.
- **A-02 🟠 No transition-completion callback in the SDK.** `CompletedTransitions` exists in `proteus-ui` but neither `proteus-sdk` nor TS surfaces it; the example uses `setTimeout(duration + 150ms)` (`destroySoon`) and `sleep()` to guess when a morph is done. Phase B: "`TransitionComplete` … used for transition chaining". Suggested: `Handle::on_transition_complete` / `SignalHandle::on_complete`, dispatched from `Proteus::tick` alongside the interaction events.
- **A-03 🟠 TS can't reach `Disabled` or `TransitioningConfig`.** `ComponentSpec.disabled` style is declarable in TS but there is no TS way to *make* a component disabled (Rust needs the `world_mut()` escape hatch); `allowInput`/`allowNavigation` (Phase B) aren't exposed by either SDK. Suggested: `Handle::set_disabled(bool)` and `ComponentSpec::transitioning(allow_input, allow_navigation)`.
- **A-04 🟠 No texture loading primitive in TS; no "ready" signal.** Phase A: `proteus.texture({ src })`, `onReady`. Reality: the only way to get pixels into the atlas from TS is to spawn a throwaway component with `image: { bytes }` off-screen and poll `bakedImageSize()` every frame (`loadBaked`/`waitForBake` in the example). Suggested: `app.loadTexture(bytes, { maxSide, eternal })` returning a `TextureHandle` (the Rust `Frame::bake_texture` already exists), plus an `onReady`/promise.
- **A-05 🟠 `mount()` hard-codes `ProteusConfig::web()`** — a TS app can't set `clear_color`, atlas sizes, `image_max_side`, or `present_mode`. Suggested: `mount(canvas, { setup, update, config })` with a `ProteusConfigDto`.
- **A-06 🟡 Navigation/keyboard is still a stub** (`stub_navigation_system`), so `focused` styles are reachable only via click-to-focus and `allow_navigation` is inert — known (PLANNING M13.7 calls it the TV unlock), just not on the M14 list.
- **A-07 🟡 Custom easing from TS is impossible** (string names only) — M14 DoD item; noting that `TransitionDefaults.custom_easings` exists in config but nothing reads it.
- **A-08 🟡 Outer/centered borders don't render** (see D-14) — the TS `Border.offset` doc admits it; the design docs don't.
- **A-09 ⚪ `Handle::split_to` docs say the source is hidden "once the transition completes"; the SDK also has no way to pass a `child_behavior` stagger** (`ChildBehaviorFn` is `proteus-ui`-only). Phase A's "iterator" model for stagger/direction isn't reachable from either SDK.
