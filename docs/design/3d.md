# 3D, and geometry other than rectangles

**Status:** a V2 candidate. A known shortcoming, listed in
[ARCHITECTURE.md](../../ARCHITECTURE.md#known-limits).

Proteus is 2D. A position's `z` only decides which component is drawn on top, `rotation` turns a
component in the screen's plane, the projection is orthographic, and there is no depth buffer.
VISION's principle 9, "Rich 2D and 3D", has components exist and transition in 3D space:
spatial interfaces, depth, perspective, and volumetric transitions.

## What 3D needs

- A perspective projection, and a camera.
- Rotation about any axis, so `QuadState`'s single `rotation` becomes an orientation.
- Depth: a depth buffer, or sorting by distance, which transparent components need anyway.
- Hit testing by casting a ray from the pointer, rather than testing a point against flat
  rectangles.
- Bakes and transitions that work in 3D, including splits and merges.

Proteus in 3D is likely to be a different mode from 2D rather than an extension of it, so the 2D
pipeline doesn't need to anticipate it.

## Geometry other than rectangles

Every component is a textured rounded rectangle, which is what lets one shader and one draw call
draw everything (see [ARCHITECTURE.md](../../ARCHITECTURE.md#rendering)). Other geometry breaks
that single buffer. VISION's "Future Geometry Types" weighs two options:

- **One instance buffer per geometry type:** one instanced draw call per type. Simple, and suited
  to native targets, where draw calls cost less.
- **Geometry atlasing:** all geometry as meshes in shared vertex and index buffers. More complex,
  but keeps one pipeline.

The choice waits for measurements on native targets. The single buffer stays the recommended
approach on the web either way.
